# UK Tick Tracker

A full-stack web application that maps tick sightings across the UK. It reads Elanco's sample
sightings API, stores the records locally, and presents them as a map, a searchable list, a
detail page for each sighting, a form for reporting a new one, and a short guide to ticks.

Built by Emmanuel Boachie ([EB-Glitch08](https://github.com/EB-Glitch08)) for Elanco's placement
programme technical task, full-stack option.
Repository: <https://github.com/EB-Glitch08/Uk-Tick-Tracker>

## What it does

- **Map of sightings.** A map of Great Britain with one circle per place. Circle size and colour
  show how many sightings are recorded there. Selecting a place opens a panel with its totals and
  species mix.
- **Filters.** Date range (year presets or exact dates), city, and species. The filters apply to
  the map, the summary panel, the trends chart and the list at the same time.
- **List view.** The same filtered data as a table, most recent first. This is also the accessible
  equivalent of the map.
- **Sighting detail.** One sighting per page, with a small map, what the tick was found on, how
  precise the location is, and nearby activity within about 10 km.
- **Report a sighting.** A stepped form for date, place, species, host, notes and an optional
  photograph. It returns a reference the reporter can quote.
- **Tick guide.** The five species in the dataset with their sighting counts, bite prevention,
  how to remove an attached tick, and a chart of sightings by month of the year.

## How to run it

You need Python 3.11 or newer, and an internet connection the first time so the application can
fetch Elanco's data. Nothing else is required: there is no npm install and no build step.

```bash
git clone https://github.com/EB-Glitch08/Uk-Tick-Tracker.git
cd Uk-Tick-Tracker
python -m venv .venv
```

Activate the virtual environment.

Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

macOS or Linux:

```bash
source .venv/bin/activate
```

Then install the dependencies and start the server.

```bash
pip install -r requirements.txt
python -m uvicorn backend.main:app --reload
```

Open <http://127.0.0.1:8000> in a browser.

FastAPI serves the frontend folder as static files, so that one command runs both halves of the
application. There is no separate frontend server.

On start-up the server creates `data/ticks.db` if it is not there, then fetches Elanco's data in a
background thread. The site opens immediately; the data appears a moment later, so refresh the
page if the map is still empty. If Elanco's API cannot be reached, the server logs a warning and
carries on with whatever it already holds. The fetch is skipped if the data was refreshed less
than fifteen minutes ago, which keeps `--reload` from calling Elanco on every file save.

The interactive API documentation, generated by FastAPI, is at <http://127.0.0.1:8000/docs>. The
raw schema is at `/openapi.json`.

Run the tests with:

```bash
python -m pytest tests
```

## Technical choices

**FastAPI and uvicorn.** The task is mostly a small JSON API over a dataset. FastAPI validates
the request body and query parameters from type hints, so the rules for a report live in one
Pydantic model rather than in hand-written checks, and it generates the `/docs` page for free.
Mounting the frontend folder as static files means the whole project runs from one process and
one command, which matters for a reviewer who has not seen it before.

**SQLite through Python's built-in `sqlite3`, no ORM.** The database is a single file, so there is
nothing to install or configure. The schema is one table, and the queries are short enough that an
ORM would add a dependency and a layer of indirection without removing any work. Write-Ahead
Logging is switched on so the site can keep reading while the import writes. The trade-off is that
SQLite suits a single-process MVP: it is not the right choice once the application runs on more
than one server, and that is noted in the improvements below.

**No frontend framework.** Plain HTML, CSS and JavaScript, with five scripts loaded in order
(`app.js`, `explore.js`, `detail.js`, `report.js`, `guide.js`), one per screen. Shared code hangs
off a single `Tracker` global. Routing is hash-based, so `#/explore`, `#/sighting/42`, `#/report`
and `#/guide` can all be linked to and shared. The reason is the same as above: no bundler, no
`node_modules`, and the source that runs in the browser is the source in the repository. The
trade-off is that there is no component model, so each screen rebuilds its section of the page
itself, and the files are longer than their framework equivalents would be.

**Hand-drawn SVG map.** The UK outline is a single SVG path with a simple equirectangular
projection, drawn from the coordinates of the fourteen cities in the data. Using it avoids a
mapping library, an external tile service and an API key, and it keeps the map keyboard operable
with ordinary HTML elements. The trade-off is that the outline is simplified, there is no zoom or
pan, and the map only shows Great Britain.

**Design.** The layout, colours and type come from a Figma design made for this task before any
code was written.

## How the data is handled

The source is Elanco's API at `https://dev-task.elancoapps.com/data`, and the records come from
`/tick-sightings`. It holds 1,000 records, which matches its own `/stats` endpoint, dated from 2012
to 2024, across 14 UK cities and 5 species.

**Fetching** (`backend/elanco.py`). Each request has a fifteen second timeout. Timeouts, network
failures and 5xx responses are retried up to three times, with a pause that grows each attempt. A
429 waits a full minute before trying again, as the API asks. A 404 or similar is not retried,
because it will not fix itself. If every attempt fails, the importer records the reason and the
site carries on with the data already stored.

**Cleaning** (`backend/cleaning.py`). Each record is handled on its own, so one bad record costs
that record rather than the whole import. City names are title-cased, so "london " and "London"
become the same place. Text fields are trimmed, a missing species becomes "Unknown", and dates are
accepted whether or not they carry a time zone.

**Duplicates.** Every row carries a `dedupe_key` built from the date, the species and the place,
and the column has a UNIQUE constraint. A second copy of the same sighting is rejected by the
database and counted as a duplicate. This is what makes the start-up import safe to repeat.

**Incomplete records.** Elanco gives a city name but no coordinates, so the coordinates are looked
up in `backend/cities.py`. A record whose city is missing or not in that list is still saved, but
flagged with `is_complete = 0`, which keeps it out of the map data while leaving it in the totals
and in search.

**Rejected records.** A record with no date, an unreadable date, or a date in the future cannot be
placed on a timeline, so it is not saved. The importer counts these and keeps the first few reasons
in its summary, which is written to the server log after each run.

The importer can also be run on its own, which prints the summary as JSON:

```bash
python -m backend.importer
```

## API endpoints

| Method | Path | Parameters | Returns |
| --- | --- | --- | --- |
| GET | `/api/health` | — | `{"status": "ok"}` |
| GET | `/api/sightings` | `date_from`, `date_to`, `city`, `region`, `species`, `on_map_only`, `limit` (1–500, default 100), `offset` | Filtered sightings, newest first, with the total |
| POST | `/api/sightings` | Body: `sighted_on`, `lat`, `lon`, `location`, `species`, `host`, `notes` | The saved sighting, its reference and any warnings |
| GET | `/api/sightings/nearby` | `lat`, `lon` (both required), `within_km` (default 10, max 200), `limit` (default 20, max 200), `exclude_id` | Sightings near a point, closest first, with distances |
| GET | `/api/sightings/{id}` | — | One sighting, or 404 |
| POST | `/api/sightings/{id}/photo` | Multipart field `photo` | The stored image path and its size in bytes |
| GET | `/uploads/{filename}` | — | A photograph attached to a sighting |
| GET | `/api/places` | — | The 14 cities with coordinates and regions |
| GET | `/api/insights/regions` | `date_from`, `date_to`, `species` | Counts per region, and the same totals folded into wider areas |
| GET | `/api/insights/locations` | `date_from`, `date_to`, `species` | One row per place with its count, latest date and species mix |
| GET | `/api/insights/trends` | `interval` (`week` or `month`), `date_from`, `date_to`, `city`, `region`, `species` | Counts per period, oldest first, with quiet periods filled in as zero |

Filters are optional and combine with AND. City, region and species matching ignores capital
letters. Every error, including validation failures, comes back in the same shape, so the frontend
handles them all one way:

```json
{"error": {"code": "validation_error", "message": "Some of the details are not valid.",
           "fields": [{"field": "lat", "message": "Input should be less than or equal to 60.9"}]}}
```

Reports are deliberately permissive where it is safe to be. A missing species is saved as
"Unknown", a date before 2012 is saved, and a spot more than 150 km from any listed city is saved
under "Other". Each of these comes back as a warning in the response rather than an error, and the
form shows them on the confirmation screen.

## Testing

83 tests, written with pytest. They run in about two seconds. Each test gets an empty database in
a temporary folder and a fake version of Elanco's API, so the suite needs no network access and
never touches the real service or the real data.

| File | Covers |
| --- | --- |
| `test_data_handling.py` | Import counts, repeat imports adding nothing, records with no date, unknown cities kept but flagged, odd capitals, dates with and without time zones, paging |
| `test_endpoints.py` | Reporting a sighting, validation failures, every filter and combination, region and trend aggregates, map data, the shared error shape, health check |
| `test_detail_and_nearby.py` | Looking a sighting up by id, 404s, the quotable reference, hosts, coordinate rounding for user reports, the nearby search and its limits, region grouping |
| `test_external_api.py` | Retries on server errors, the pause after a 429, giving up after three attempts, not retrying a 404, no internet, a reply of the wrong shape, and the site still working while Elanco is down |
| `test_photos.py` | Uploading and serving a photo, refusing a file that is not really an image, refusing one that is too large, never using the name the file arrived with, and not serving made-up filenames |
| `test_startup.py` | The first run filling itself with data, starting with Elanco unavailable, saving a report while the import is running, and not refetching on a quick restart |

```bash
python -m pytest tests
```

GitHub Actions runs the same suite on every push to `main` and on every pull request, on Python
3.11 and 3.13.

## Accessibility

The four screens were audited with axe-core against WCAG 2.1 AA, and each reports zero violations.

- Every screen is keyboard operable, including the map. Each place on the map is a focusable
  control that responds to Enter and Space, and the list view gives the same data as a table for
  anyone who would rather not use the map at all.
- There is no horizontal scrolling at 390px, 768px or 1440px.
- The map and both charts carry a text description of their contents, so the figures are available
  without reading the picture.
- Map colours vary in lightness as well as hue, so the bands can still be told apart without
  normal colour vision, and the legend states the numbers.
- There is a skip link, headings are in order, form errors are listed above the form with links to
  the fields they belong to, and the current screen is marked with `aria-current` for screen
  readers as well as visually.

## Privacy

A person reporting a tick usually does it where they found it, which may be their home or a walk
they take often. The exact coordinates are kept in the database, because they are what was
reported, but every response rounds a user's own coordinates to two decimal places, which is about
a kilometre, and labels them "about 1 km". Elanco's own records already sit on a city centre, so
they are returned unchanged and labelled "city centre".

Uploaded photographs are checked by their opening bytes rather than the type the browser claims,
capped at 10 MB as the bytes arrive, and saved under a name the server generates, so a filename
cannot decide where a file is written. Only names of exactly that shape are served back.

## Things I would improve with more time

- **The UK outline is simplified.** It is one hand-drawn SVG path, and Scotland in particular is
  rough. Real boundary data, generalised to the size the map is drawn at, would be more honest and
  would let the map show Northern Ireland.
- **City attribution is coarse.** A sighting within 150 km of one of the fourteen listed cities is
  attributed to that city. Anywhere further away falls under "Other", so Northern Ireland and much
  of the Highlands have no region at all. Proper boundary lookup would replace the distance test.
- **Duplicated filter code.** `build_where` in `backend/insights.py` and the equivalent block in
  `backend/search.py` do the same job twice. They should be one shared function, as the two have
  already drifted slightly: search also has `on_map_only`.
- **The trends chart starts at the first month that has data**, not at the start of the range the
  user asked for, because empty periods at either end are trimmed before drawing. That reads
  better, but it means the chart's axis does not always match the filter above it.
- **No paging in the interface.** The API supports `limit` and `offset`, and that is tested, but
  the list view only ever asks for the 50 most recent rows. It needs page controls, or loading
  more as the user scrolls.
- **No authentication or moderation.** Anyone can post a report and it appears straight away.
  A real version needs accounts, rate limiting, and a way for someone to review reports and
  photographs before they are published.
- **SQLite would have to go.** It is a single file written by a single process, which is fine for
  this MVP but will not work behind more than one server. PostgreSQL would be the replacement, and
  it would also handle the distance queries in SQL instead of in Python.
- **The import is all-or-nothing.** It fetches the whole dataset each time and relies on the
  duplicate key to discard what is already held. Fetching only what has changed since the last run
  would be cheaper if the dataset grew.
